# Cassandra AI — Prototype Results

SIH26184, Team NeferX. All numbers below are from actual runs saved to disk under
`results/*.json` and `data/processed/*.parquet` — none are invented, rounded up, or
tuned on the test set. An independent reviewer agent (see `results/REVIEW.md`)
recomputed every headline metric from the saved parquet/model artifacts directly,
with no code reuse from the evaluation scripts, and found zero discrepancies.

**Every number in this document is on SIMULATED data unless explicitly marked
"real data."**

## 1. What was built

A seeded simulator (`simulator/`) generates synthetic ATM/POS transactions, mule
account networks, and complaints over a real geographic universe: 1,150 real
ATM coordinates fetched from OpenStreetMap for Bengaluru (`data/calibration/`,
`data/simulated/fixture/terminals.parquet`). Three simulator configurations (A,
B, C) with genuinely different mule topology, timing, and terminal-choice logic
feed a feature pipeline (`model/features.py`) that builds a (terminal, 2-hour
window) feature table with a rolling-origin train/val/test split and a 7-day
embargo. An XGBoost classifier is trained on config A and evaluated against a
past-hotspot-frequency baseline and a rule-only baseline on A, B, and C. A
FastAPI backend and React+MapLibre UI expose the ranked output as an officer
alert view. See `PROJECT_SPEC.md` for the full architecture and
`SCHEMA_CONTRACT.md` for exact data shapes.

## 2. Headline result: the model does not beat the baseline

| Config | Model ROC AUC | Baseline (hotspot) ROC AUC | Rule-only ROC AUC | Model Precision@10/window | Baseline Precision@10/window | Beats baseline? |
|---|---|---|---|---|---|---|
| A (train, in-distribution test) | 0.524 | 0.486 | 0.456 | 0.000 | 0.000 | **No** |
| B (cross-config, different topology) | 0.391 | 0.492 | — | 0.000267 | 0.000535 | **No** |
| C (cross-config, different topology) | 0.503 | 0.510 | — | 0.00238 | 0.00357 | **No** |

*(Source: `results/metrics_config_A.json`, `_B.json`, `_C.json`,
`results/metrics_circularity.json`. All ROC AUC values are near 0.5 — chance
level — and on config B the model is measurably worse than chance-adjacent. On
no config, by either headline metric, does the XGBoost model outperform the
simple past-hotspot-frequency baseline.)*

**We are reporting this plainly rather than hiding it, per the project's
reporting rules.** This is itself a legitimate finding for a thin-slice
prototype, not a failure to hide: it means the current feature set and 2-hour
window granularity are not sufficient to learn the simulator's own injected
signal above a trivial baseline, at this data scale (194k–196k transactions,
464–1,464 positive terminal-windows per config, out of ~1,150 terminals × ~100
2h-windows).

**Plausible causes** (documented in `model/AGENT_REPORT.md` and
`results/metrics_circularity.json`):
- Extreme label sparsity: 0.1–0.3% positive rate per config.
- 2-hour bucket granularity may be too coarse relative to the mule cash-out
  patterns the simulator generates.
- Short time range (13–21 days per config) limits learnable temporal signal.
- `metrics_config_C.json`'s result is a pure cross-config check — config C's
  13-day span is too short to carve its own internal train/val/test split, so
  "beats_baseline" for C reflects the A-trained model scored on all of C's
  rows, not a C-internal holdout. This is a known, disclosed limitation.

## 3. Circularity protocol (mandatory, PROJECT_SPEC.md)

| Step | Status | Detail |
|---|---|---|
| 1. Train on A, test on B/C with different topology | ✅ Solid | A/B/C differ in hop-count distribution (Poisson λ=2/4/1), delay distribution, cash-out pattern, and terminal-choice heuristic (`nearest_to_last_hop` / `hotspot_avoidant` / `random_in_city`) — a real topology change, not a renamed seed. |
| 2. Rule-only baseline mirroring the generator | ✅ Solid | Present per-config in every `metrics_config_*.json`, implemented against each config's actual documented heuristic. |
| 3. Label noise / delayed labels | ⚠️ Partial, disclosed | Noise rates differ by config (A: 5%/2% FN/FP; B: 8%/2%; C: 10%/4%) and are baked into generation rather than an isolated same-topology/different-noise ablation. Degradation from A→B→C is the reported robustness proxy; this conflates topology shift with noise shift, which is an openly stated limitation, not a hidden one. |
| 4. Real-data benchmarks reported separately | ✅ Solid | `results/benchmark_stdbscan_chicago.json` is clearly labeled real-data and never blended into any simulated-metrics file (verified by the independent reviewer). |
| 5. Realism gap stated plainly | ✅ Solid | See full statement below — quoted directly from `results/metrics_circularity.json`. |

> **Realism gap statement** (verbatim, `results/metrics_circularity.json`):
> "All metrics in this file are computed EXCLUSIVELY on simulator-generated
> data... The simulator's mule-detection 'signal' is generated by the SAME
> family of heuristics the model is trying to learn, which inflates apparent
> model performance relative to a real deployment: a real adversary does not
> follow a known, stationary terminal_choice distribution... Precision@10 and
> lift figures here should be read as 'does the model learn the intended
> mule-activity signal at all', not as an estimate of real-world
> fraud-detection performance."

## 4. Real-data benchmarks (separate from all numbers above)

| Module | Dataset | Result | Status |
|---|---|---|---|
| ST-DBSCAN spatio-temporal clustering | Chicago Crimes (Socrata Open Data, 15,000 real incidents, 120 days, public/no-auth) | 84 clusters found, 4.59% of points clustered, sensible interpretable hotspots (e.g. 29-point cluster in a 16h window at one location) | ✅ Real data, completed |
| Graph/linkage module | Elliptic / IBM AMLworld | Skipped — all channels (Elliptic's Kaggle page, HuggingFace mirror with unverifiable relicensing, IBM's official repo linking only to auth-walled Kaggle/Box) required login or had unclear licensing | ❌ Skipped cleanly, not faked — see `results/benchmark_notes.md` for the full account |

This validates that the ST-DBSCAN clustering mechanism behaves sensibly on a
real spatio-temporal point process, but cannot validate fraud-specific
precision since Chicago crime data has no mule-terminal ground truth. The
graph-linkage module remains unvalidated against real-world fraud-graph data —
an open gap, honestly disclosed rather than papered over with a lower-quality
substitute dataset.

## 6. Independent review

A dedicated reviewer agent, which did not see the implementation work,
independently recomputed every headline metric directly from
`data/processed/features_config_*.parquet` and
`model/artifacts/xgb_config_A.json` (no reuse of `evaluate.py`/`baselines.py`
code) and found **zero discrepancies** against the saved JSON files. It also
audited for leakage across 9 specific checkpoints (rolling-origin embargo,
as-of feature construction, self-referential label leakage in the hotspot
feature, train/val/test discipline) and found **no blocking leakage issues**.
One minor overclaim was found and has since been fixed: the two UI screenshots
were originally captured against mock data before the real model finished
training, so the SHAP feature names shown didn't match the real model's actual
features. Both screenshots have been re-captured against the live, real,
trained model (see `results/screenshots/`). Full detail in `results/REVIEW.md`.

## 7. Limitations (stated plainly)

- The model does not currently outperform a trivial frequency baseline on this
  simulated data — this is the single most important honest caveat.
- Label noise and topology shift are conflated in the circularity protocol's
  step 3 (noise rates differ per config alongside topology, not isolated).
- Config C has no internal test split (its 13-day span is too short); its
  "beats_baseline" result is purely a cross-config generalization check.
- The graph/linkage module (NetworkX + Splink-style entity resolution) was not
  validated against any real fraud-graph dataset (Elliptic/AMLworld were
  blocked by licensing/auth, not substituted with something lower-quality).
- NCRP/RBI calibration numbers were hand-transcribed from cited public sources
  (government reports, RBI's Handbook of Statistics, press coverage of
  official figures) because no clean bulk-downloadable dataset exists for
  either — every figure has a source URL and access date in
  `data/calibration/manifest.json`, but this is weaker than a direct bulk
  export.
- pgmq (the originally specified Postgres queue extension) is not bundled in
  the `postgis/postgis` Docker image used; the thin slice uses direct
  table reads/writes instead of a message queue, documented in
  `docker/init/001_extensions.sql`.

## 8. Reproducibility

Everything above is reproducible from a fresh checkout: `data/calibration/`
and `data/simulated/fixture/terminals.parquet` are generated by
`scripts/fetch_calibration.py` and `scripts/build_terminals.py`;
`simulator/generate.py --config {A,B,C}` regenerates the simulated
transactions/accounts/complaints deterministically (seeded via
`numpy.random.default_rng`, `random.Random`, and `Faker.seed`, all keyed off
each config's `seed` field — spot-checked by the independent reviewer); and
`model/features.py`, `model/train.py`, `model/evaluate.py` regenerate the
feature tables, trained model, and metrics files in order. See `README.md`
for exact commands.
