# Prototype Report — Cassandra AI (SIH26184)

Every number below comes from an actual run saved to disk, with the file that produced
it named next to it. Where something was not measured, this says so explicitly rather
than estimating.

## 1. What was built

Cassandra AI is a thin, end-to-end pipeline for ranking ATM/POS terminals by
mule-network withdrawal risk in 2-hour windows: a seeded simulator generates
transactions, mule account chains, and complaints over a real geographic universe
(1,150 real Bengaluru ATM coordinates from OpenStreetMap); a feature-build step
constructs an as-of (terminal, 2-hour-window) feature table with a leak-free
rolling-origin split; an XGBoost classifier is trained and compared against two
baselines; a FastAPI backend serves ranked, SHAP-explained results to a React +
MapLibre map UI with an officer alert view.

**Architecture:**

| Component | Technology | Version |
|---|---|---|
| Simulator | Python, NumPy, Faker | Python 3.11.7 |
| Spatial index | H3 | 4.5.0 |
| Storage | Parquet (primary); Postgres/PostGIS provisioned | PostGIS 16-3.4 (Docker, not currently in the read path) |
| Feature engineering | pandas, NetworkX (as-of graph) | pandas 3.0.6, NetworkX 3.6.1 |
| Candidate clustering | scikit-learn DBSCAN (space+time rescaled) | scikit-learn 1.9.1 |
| Model | XGBoost | 3.2.0 |
| Explainability | SHAP (TreeExplainer) | 0.51.0 |
| API | FastAPI + Uvicorn | FastAPI 0.142.2 |
| UI | React + TypeScript + MapLibre GL JS, Vite | Vite 5.4.21 |
| Experiment tracking | MLflow (local file store) | 3.16.1 |

**Data flow:** `simulator/configs/{A,B,C}.yaml` -> `simulator/generate.py` ->
`data/simulated/config_X/{accounts,transactions,complaints,terminals}.parquet` ->
`model/features.py` -> `data/processed/features_config_X.parquet` ->
`model/train.py` -> `model/artifacts/xgb_config_A.json` -> `model/predict.py` ->
`api/app/data_source.py` -> `api/app/main.py` -> `ui/` (React/MapLibre).

**Status:**
- **Fully working**: simulator (3 configs), feature pipeline, XGBoost training,
  evaluation harness (rolling-origin + circularity protocol), FastAPI backend on
  real model output, React/MapLibre UI with both required views, calibration data
  fetch, ST-DBSCAN real-data sanity check (Chicago Crimes).
- **Partial**: label-noise robustness (noise rate differs per config but is
  conflated with topology/timing shift, not an isolated ablation — see §5);
  lead-time measurement (attempted, found genuinely not computable from current
  simulator output — see §4).
- **Mocked**: SMS alerts (MSG91) — logs only, never calls a real API, by design.
- **Missing / not attempted**: graph/linkage module validation against real
  fraud-graph data (Elliptic/AMLworld both blocked by auth walls — see §6);
  pgmq message queue (not bundled in the Postgres/PostGIS Docker image used;
  direct table/file access substituted); Prefect orchestration (plain scripts
  used instead); Splink entity resolution (not reached — NetworkX used for the
  graph feature instead).

## 2. Data

**Real data used:**
- 1,150 real ATM coordinates for Bengaluru, fetched from OpenStreetMap's Overpass
  API (`node["amenity"="atm"]`, bounding box covering greater Bengaluru). Raw
  response frozen at `data/raw/osm_atms_bengaluru.json`, checksummed in
  `data/calibration/manifest.json`. Only the `bank` (sampled from 6 real Indian
  bank names) and `install_date` columns on top of these real coordinates are
  synthetic — disclosed in `data/calibration/README.md`.
- NCRP and RBI calibration numbers, hand-transcribed from cited public sources
  (government Rajya Sabha statements, RBI's Handbook of Statistics as reported
  by business press, NCRB "Crime in India" figures) into
  `data/calibration/*.csv`, each with a source URL and access date in
  `manifest.json`. No bulk-downloadable open dataset exists for either NCRP or
  RBI figures, so no direct CSV/API pull was possible — this is the one area
  where "real" means "real but secondhand-cited," not a direct bulk export.
  Explicitly skipped: NCRP's own portal dashboards (no accessible bulk export),
  a PIB press release page and an MHA Lok Sabha PDF (both HTTP 403), and RBI's
  ATMView.aspx pages (interactive ASP.NET, not flat-downloadable).
- 15,000 real Chicago crime incidents (Socrata Open Data API, ~120 days,
  2026-06-02 to 2026-09-29), used only to sanity-check the ST-DBSCAN clustering
  module — see §6.

**Simulated data:** all transactions, accounts, mule chains, and complaints are
generated by `simulator/generate.py`. Three configurations (A, B, C):

| Config | Accounts | Mule accounts | Transactions | Mule-hop txns | Complaints | Days | Seed |
|---|---|---|---|---|---|---|---|
| A (fast short-chain) | 2,101 | 1,061 | 194,072 | 1,061 | 136 | 21 | 42 |
| B (slow long-chain) | 3,187 | 2,177 | 196,452 | 3,241 | 107 | 32* | 43 |
| C (fan-out structuring) | 2,254 | 1,264 | 131,948 | 3,096 | 84 | 14 | 44 |

\* B's configured range is 22 days; actual output spans 32 days because long/slow
mule chains are clipped at `end + 10 days` rather than resampled (documented
deviation, `simulator/README.md`).

Label (terminal, 2-hour window) positive rates: A 0.160% (464 positive windows out
of ~289,800), B 0.204% (900 of ~441,600), C 0.758% (1,464 of ~193,200). This is
intentionally a rare-event problem, not artificially balanced.

**Public datasets used, and for what:** OpenStreetMap (real terminal geography),
NCRP/RBI figures (background calibration context, not fed into the model
directly), Chicago Crimes via Socrata (ST-DBSCAN sanity check only). **Skipped:**
Elliptic and IBM AMLworld (graph/linkage module benchmark) — both datasets'
only authoritative distribution channels (Kaggle, or Kaggle/IBM Box for
AMLworld) require interactive login; two Hugging Face mirrors existed but with
unverifiable third-party relicensing claims, so neither was used. See
`results/benchmark_notes.md` for the full account of exactly what was tried.

## 3. Simulator

Config-driven (`simulator/configs/{A,B,C}.yaml`), seeded, no LLM involved in
generating any numeric or tabular data.

| Parameter | A | B | C |
|---|---|---|---|
| Hop count distribution | Poisson(lambda=2) | Poisson(lambda=4) | Poisson(lambda=1), wide fan-out |
| Mule branches per victim | 2-5 | 3-7 | 6-14 |
| Delay between hops | lognormal(mu=1.5, sigma=0.8), median ~4.5h | lognormal(mu=2.6, sigma=1.3), median ~13h, heavy tail | lognormal(mu=1.1, sigma=1.0) |
| Cash-out pattern | single large withdrawal | structured, below-threshold, repeated | structured, below-threshold, via many parallel accounts |
| Terminal choice | nearest to last hop | hotspot-avoidant | uniformly random |
| False-negative rate | 5% | 8% | 10% |
| False-positive rate | 2% | 2% | 4% |
| Label delay | uniform(0, 14) days | uniform(0, 21) days | uniform(0, 10) days |
| Seed | 42 | 43 | 44 |

Reproducibility: seeding uses `numpy.random.default_rng(seed)`, `random.Random(seed)`
(not the unseeded global `random` module — confirmed by code inspection across
~20 call sites), and `Faker.seed(seed)`, plus belt-and-suspenders global
`random.seed`/`np.random.seed` calls. Verified bit-for-bit reproducible: running
the generator twice with the same seed produces identical output DataFrames.

**Seed variance is small relative to how far every value sits from "beats
baseline."** Seed standard deviation is roughly 1-5% of each metric's range,
while ROC AUC stays within the 0.39-0.58 near-chance band on every single seed
on every config — the headline finding (model does not beat baseline) is not a
seed-lucky or seed-unlucky artifact.

**Baselines are deterministic** (verified by code inspection — `baselines.py`
contains no random-number generation), so they are reported as single values
with no seed variance, not fabricated as having spread.

**PR-AUC note:** `average_precision_score` and `auc(precision_recall_curve)`
("trapezoidal PR-AUC") sometimes diverge noticeably at this sub-1%-positive-rate
scale (e.g. seed 44, config A: average precision 0.0025 vs trapezoidal PR-AUC
0.0125) — both are reported since they are different area estimators and
neither is simply "the" correct one at this label sparsity.

### Lead time: **not measured** — found to be genuinely not computable

The task asked for minutes between a complaint being filed and the model's
predicted high-risk window. This was attempted (`model/lead_time.py`,
`results/metrics_lead_time.json`) and found not to be honestly computable from
the data as currently persisted: the label join that `model/features.py` uses
(`complaints.account_id` vs `transactions.account_id`) matches only 3 of 136
config-A complaints to any transaction at all, and all 3 are injected
false-positive-noise complaints against ordinary benign accounts with zero
mule-hop transactions — not a withdrawal event by the simulator's own ground
truth. Genuine mule-ring withdrawals exist in `transactions.parquet`
(`is_mule_hop=True`, with exact timestamps) but are tied to freshly-minted mule
account IDs that are never linked back to the originating complaint in any
persisted table — that link exists only in memory during simulation
(`simulator/lib/generate_core.py`'s `ring_terminals_hit`) and is discarded
before any file is written. Computing a real lead time would require persisting
one additional field (a `ring_id`/`complaint_id` foreign key on mule
transactions, or a separate `rings.parquet` table) — this is a concrete,
scoped follow-up, not a dead end, and is documented in full diagnostic detail
in `results/metrics_lead_time.json`.

## 5. Generalisation (circularity test)

Trained once on config A, evaluated on A (in-sample test split), B, and C
(cross-config, never trained or tuned on any row of either).

| Metric | A (in-sample) | B (cross-config) | C (cross-config) |
|---|---|---|---|
| ROC AUC | 0.524 | 0.391 | 0.503 |
| vs. baseline ROC AUC | 0.486 | 0.492 | 0.510 |
| Does it still beat rule-only baseline? | No | No (rule-only not computed for B — see note below) | No |

Performance does not "drop" from A to B/C in the usual sense of a model that
was good in-sample and degrades out-of-sample — it is near chance on A already,
and stays in the same near-chance band (0.39-0.58 ROC AUC) across all three.
Config B's cross-config ROC AUC (0.391) is below 0.5, i.e. the model's ranking
is directionally worse than random on B — reported plainly, not minimized.

The three configs differ genuinely in topology and timing, not just by seed:
hop-count distribution (Poisson lambda 2 vs 4 vs 1), delay distribution, cash-out
pattern, and critically the terminal-choice heuristic (nearest-to-last-hop vs
hotspot-avoidant vs uniformly random — three different spatial strategies). This
was confirmed by diffing `simulator/configs/A.yaml` against `B.yaml` and
`C.yaml` directly, not just asserted.

**Realism gap statement** (quoted verbatim from `results/metrics_circularity.json`):
> "All metrics in this file are computed EXCLUSIVELY on simulator-generated
> data... The simulator's mule-detection 'signal' is generated by the SAME
> family of heuristics the model is trying to learn, which inflates apparent
> model performance relative to a real deployment: a real adversary does not
> follow a known, stationary terminal_choice distribution... Precision@10 and
> lift figures here should be read as 'does the model learn the intended
> mule-activity signal at all', not as an estimate of real-world
> fraud-detection performance."

## 7. Explainability

Top 5 features by mean absolute SHAP value on config A's held-out test set
(computed directly via `shap.TreeExplainer`, not estimated):

| Rank | Feature | Mean \|SHAP\| | Plain-English reading |
|---|---|---|---|
| 1 | `txn_amount_sum_168h` | 0.159 | Total transaction value at this terminal over the past 7 days — the single strongest signal the model uses, suggesting it leans heavily on a week-long volume trend rather than short-term spikes. |
| 2 | `complaint_density_kring` | 0.131 | How many complaints have been filed near this terminal (H3 k-ring neighborhood) as of this window — a proxy for "this neighborhood has recent fraud activity," which is sensible as a feature but is also exactly the kind of signal that could overlap with the past-hotspot baseline it's being compared against. |
| 3 | `txn_amount_sum_24h` | 0.088 | Total transaction value in the last 24 hours — a shorter-horizon version of feature #1. |
| 4 | `txn_amount_sum_6h` | 0.057 | Total transaction value in the last 6 hours — an even shorter-horizon volume signal. |
| 5 | `txn_amount_sum_2h` | 0.055 | Total transaction value in the current 2-hour window itself — the most immediate signal, but ranked below the longer-horizon volume features, suggesting the model is not simply reacting to an in-window spike. |

Notably, `graph_dist_to_known_mule` (distance in the as-of transaction graph to
a known complaint-linked account) ranks 9th of 11 features (mean |SHAP| 0.013),
and `past_hotspot_freq` — the same feature the baseline is built on — ranks 8th
(0.015). Despite being given graph and baseline-equivalent information, the
model's single strongest signal is a raw transaction-volume sum, which is
consistent with the near-chance headline performance: the model has not learned
to weight the arguably more fraud-specific features (graph distance, complaint
density, historical hotspot rate) over simple volume.

## 10. Honest limitations

- **The model does not beat either baseline on any configuration, on any of 5
  seeds.** ROC AUC stays in the 0.39-0.58 range — essentially chance,
  occasionally worse than chance (config B, 0.39). This is the single most
  important caveat and should not be downplayed.
- **Where results might be inflated**: the simulator's mule-detection "signal"
  (terminal proximity to recent activity, complaint density) is generated by
  the same family of heuristics the model is trying to learn — a real adversary
  does not follow a known, stationary terminal-choice distribution the way the
  simulator's configs do. Cross-config generalisation (A->B, A->C) is the best
  available proxy for this gap at this scale, but is not a substitute for
  real-data validation.
- **Leakage checks done** (see `results/VERIFICATION.md` for the full audit,
  independently recomputed from saved parquet/model files, not just read from
  code): rolling-origin split verified to have a true >=7-day embargo gap with
  zero overlap directly on the parquet files; the past-hotspot-frequency
  feature verified via unit test to exclude the current window's own label
  before averaging; all as-of features (rolling counts, complaint density,
  graph distance) verified to use strict `<` timestamp comparisons; test split
  verified to be touched exactly once, after the model was already persisted.
  **No blocking leakage issues were found.**
- **Config C has no internal test split** — its 13-day span is too short to
  carve out train + 2x embargo + val + test, so its "beats_baseline" result is
  entirely a cross-config check (A-trained model scored on all of C), not a
  true C-internal holdout.
- **Label noise and topology shift are conflated** in the circularity
  protocol's robustness check — noise rates differ per config alongside
  topology, not as an isolated ablation (see §5, §4).
- **Lead time could not be computed** — a structural gap in what the simulator
  persists (no complaint-to-withdrawal foreign key survives to disk), not an
  estimation failure. See §4 for the concrete fix needed.
- **Graph/linkage module unvalidated against real fraud-graph data** — Elliptic
  and AMLworld were both blocked by auth walls, and no substitute was used.
- **NCRP/RBI calibration numbers are hand-transcribed from press coverage of
  official figures, not a direct bulk-data pull** — a few figures show minor
  cross-source variance (e.g. Bengaluru 2023 case count cited as both 17,631
  and 17,623 by different outlets), both noted rather than silently resolved.
- **What real data would change**: real transaction data would let the model
  learn genuine, non-stationary fraud patterns instead of the simulator's own
  heuristics, which is the only way to know if the near-chance result is a
  property of this feature set/data scale or a property of a model trained on
  signal that is too similar to its own evaluation.

## 11. Failures and surprises

- **A severe performance bug was found and fixed during the build**: an early
  version of the graph-distance feature rebuilt a full NetworkX graph and ran a
  fresh BFS for every 2-hour window (~250 windows for config A, each
  re-scanning a 7-day lookback slice with ~84-window overlap with its
  neighbors) — this hung for over 1,000 CPU-seconds before being caught and
  fixed by switching to a single cumulative graph swept forward in time order.
  Fixed feature-build time: 36s for config A.
- **A silent correctness bug was found during the same pass**: the
  rolling-origin split applied train/val fractions against the *full* time
  span before subtracting embargo time, which on config A's 20-day span left
  zero rows tagged "test" — the fractions, computed against the full 20 days,
  consumed everything before reaching the test portion. Fixed by applying
  fractions to the time remaining after both embargoes are reserved.
- **Precision@10 was originally computed globally across the entire flattened
  test table** (asking "are any of the single 10 highest-scored rows in the
  whole table positive," an near-impossible target with positives spread 1-5
  per window across dozens of windows) rather than per-window, which is what
  the actual API/officer workflow uses (ranking within one as-of window at a
  time). Fixed by adding a per-window precision@k metric and making it the
  headline comparison.
- **The API's real-model path initially took minutes per request** because it
  scored the model's entire historical feature table (~290,000 rows) through
  SHAP on every call instead of just the current window. Fixed by filtering to
  the latest window before scoring (~1,150 rows), bringing warm latency to
  ~6.5ms.
- **Lead time was attempted and found not computable**, not simply skipped —
  see §4 and §10 for the full diagnosis and what would need to change in the
  simulator to make it computable.
- **What was cut**: pgmq (not bundled in the Postgres/PostGIS image used, and
  judged not worth the extra install time for a thin slice — direct
  table/file access substituted); Prefect orchestration (plain scripts used
  instead); Splink entity resolution (NetworkX used directly for the graph
  feature instead, since the graph need was narrow enough not to require a
  dedicated linkage library).
- **What's next**: persist a complaint-to-mule-ring foreign key in the
  simulator output to make lead time computable; obtain Kaggle credentials to
  run the graph/linkage module against Elliptic/AMLworld; investigate why
  volume-based features dominate SHAP over the arguably more fraud-specific
  graph-distance and complaint-density features, which may point toward
  feature scaling, window granularity, or additional engineered features as
  the next lever to try before concluding XGBoost itself is the wrong model
  for this problem.

## 12. Cost and effort

**To run the pilot as built** (not a production deployment):
- CPU: 4+ cores recommended (feature build and multi-seed training are
  CPU-bound; measured on a 6-core AMD Ryzen 5 5500U).
- RAM: under 2 GB observed for the full pipeline against the current data
  scale (1,150 terminals, ~130-200k transactions per config); not stress-tested
  at larger scale.
- Storage: under 50 MB for all generated Parquet data across all three configs
  plus the trained model artifact; screenshots and calibration CSVs add a few
  MB more. Postgres/PostGIS, if used, needs its own container volume
  (unmeasured, default Docker volume growth).
- No GPU required.

**Estimated monthly cloud cost** (ALL FIGURES ARE ESTIMATES, not measured):
a small single-instance deployment (e.g. a 2 vCPU / 4 GB cloud VM running the
FastAPI backend plus a small managed Postgres instance, if the Postgres layer
were activated) would likely cost on the order of **$30-80/month** on a typical
cloud provider's smallest general-purpose tier, before accounting for the
Overpass/OSM refresh cadence (free), any SMS provider costs (MSG91 is mocked
here, not budgeted), or data egress. This is a rough order-of-magnitude
estimate for a pilot-scale deployment, not a sized production estimate — no
load testing was done to validate it against real traffic.
